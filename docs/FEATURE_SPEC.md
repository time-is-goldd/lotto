# FEATURE SPEC — 기능별 상세 스펙 (Luck Platform / MoSCoW 개정판)

> v2.0. [[MASTER_PRD]] §0의 Luck Platform 구조에 따라 기능을 브랜치별로 재편했다. 모든 기능에 [[ROADMAP]] §1의 MoSCoW 등급을 명시한다. **행운 다이어리를 최상단 §0으로 승격**한 것이 v1.0과 가장 큰 차이다.

---

## 0. Lucky Journal — 행운 다이어리 [플랫폼 핵심 기능]

### 0.1 목적
단순 저장소가 아니라 "내 행운의 역사"를 기록하는 곳. 플랫폼 재방문의 구조적 이유가 되어야 한다 ([[MASTER_PRD]] §0). [[CRITICAL_REVIEW]] U-01에서 지적된 "당첨확인/당첨사례 명칭 충돌"을 당첨확인 기능을 다이어리에 흡수시킴으로써 해결한다.

### 0.2 하위 구성 (MoSCoW)
| 하위 기능 | URL | MoSCoW |
|---|---|---|
| 히스토리 (생성/저장 목록) | `/my/journal/history` | **Must** |
| 당첨 확인 결과 | `/my/journal/results` | **Must** |
| 행운 캘린더 | `/my/journal/calendar` | Should |
| 내 꿈 기록 | `/my/journal/dreams` | Should |
| 운세 조회 이력 | `/my/journal/fortune-history` | Should |
| 월간/연간 통계 | `/my/journal/stats` | Could |
| 연말 Luck Report | `/my/journal/yearly-report` | Could (Phase 3 목표) |

### 0.3 데이터 항목 (요구사항 전체 반영)
생성 번호 / 저장 번호 / 구매 여부(자진기록) / 구매 금액(자진기록) / 당첨 결과(자동) / 꿈 기록(자유기록) / AI 운세 기록(자동 누적) / 생성 당시 추천 이유(자동 스냅샷) / 행운 메모(자유기록) / 가장 많이 생성한 번호(계산) / 최고 당첨 기록(계산) / 월간·연간 통계(계산) / 행운 캘린더(뷰) / 번호 생성 히스토리(목록)

데이터 모델은 [[DATABASE_SCHEMA]] §3.3(`user_numbers` 확장 컬럼), §3.6(`dream_journal_entries`), §3.8(`user_period_stats`) 참조.

### 0.4 UX 설계
- 마이페이지/하단탭 최상단에 "행운 다이어리" 진입점 배치 (구 "당첨확인" 탭 자리를 대체, [[INFORMATION_ARCHITECTURE]] §1.2)
- 로그인 회원의 홈 화면에는 "이번달 요약" 위젯 상시 노출: "이번달 N번 생성, M번 구매 기록, 최고 K개 일치"
- **손익 표기는 신중하게**: 구매금액 대비 당첨금 비교는 "재미로 보는 기록"으로 프레이밍하고, 절대 손익을 부각하는 자극적 UI(예: 큰 빨간 손실 그래프)를 사용하지 않는다. 오히려 과다 지출 패턴 감지 시 "이번달 구매금액이 평소보다 많아요" 같은 책임감 있는 넛지를 Could 등급으로 고려한다.

### 0.5 연말 Luck Report (Spotify Wrapped 스타일)
- 매년 12월 말~1월 초, 회원별로 자동 생성: 총 생성 횟수, 가장 많이 뽑은 번호, 최고 당첨 기록, 가장 많이 꾼 꿈 키워드, 올해의 운세 하이라이트 등을 카드 형태로 구성
- 카카오 공유 최적화 (§8 참조) — 공유 시 신규 유입을 만드는 시즌 바이럴 장치
- 기본 리포트는 무료, 상세 PDF/고급 디자인 버전은 유료 옵션으로 [[FEATURE_SPEC]] §9 멤버십/§10 쇼핑몰과 연계 가능 (수익화 모델, [[CRITICAL_REVIEW]] §7)
- **MoSCoW: Could (Phase 3 목표)**

### 0.6 Feasibility 주의사항
"구매여부/구매금액 자동 기록"은 동행복권이 개인별 구매내역 공개 API를 제공하지 않으므로 **자동 검증이 불가능하며 자진 신고(수동 토글) 방식으로만 구현 가능하다.** UI 문구에서 이를 "자동 추적"으로 오인시키지 않는다. 동행복권 계정 자격증명을 저장/스크래핑하는 방식은 법적·보안 리스크가 크므로 채택하지 않는다.

## 3. Fortune — AI 운세 (간소화, [[CRITICAL_REVIEW]] P-02 반영)

### 3.1 문제 재검토
v1.0은 "생년월일 기반 명리학 규칙 엔진"을 직접 구현하는 것을 전제했다. 이는 정확한 만세력(간지) 계산과 오행 해석을 요구하는, 그 자체로 큰 프로젝트다. 1인 개발 MVP에는 부적합하다.

### 3.2 개정된 접근
- **MVP(Should)**: 생년월일 → 띠(12지) 계산(단순 산술, 구현 쉬움) + 사전 작성된 띠별/월별 템플릿 문구 조합으로 "종합운세/행운지수/추천번호" 3개 항목만 제공.
- **Phase 2 이후(Could)**: 나머지 7개 항목(오늘의 기운/금전운/행동지침/피해야할행동/행운색/행운방향/행운시간)을 추가하며, 이때 LLM API 호출로 문구를 생성하는 방식을 우선 검토(직접 명리학 엔진 구현보다 개발 리소스 절약). 동일 입력값에 대해 하루 동안 동일 결과가 나오도록 캐시 키를 `입력값+날짜`로 고정해 일관성을 유지한다.

### 3.3 개인정보 처리 — 유지
비로그인도 이용 가능, 결과는 `share_id` 기반 임시 발급, 로그인 시에만 영구 저장.

## 8. Growth — 친구 초대 시스템 (신규)

### 8.1 목적
[[CRITICAL_REVIEW]] G-01(레퍼럴 부재)을 해결하는 핵심 바이럴 장치.

### 8.2 기능 구성
| 기능 | MoSCoW |
|---|---|
| 친구에게 번호 공유 (카카오, §9와 연동) | Must (§9.1과 동일 기능) |
| 친구 초대 링크(`/invite/[inviteCode]`) | Could (Phase 4) |
| 친구와 배틀 | Should (Phase 4, §5.3) |
| 친구 랭킹 | Should (Phase 4, §5.4) |

### 8.3 보상 설계
초대한 사람과 초대받은 사람 양쪽에 **비현금성 보상**(예: "프리미엄 운세 1회 무료", "배틀 우선참여권") 지급. `referrals` 테이블 ([[DATABASE_SCHEMA]] §3.17). 현금·포인트 환전 설계는 하지 않는다 ([[MASTER_PRD]] 비목표, 전자금융거래법 리스크 회피).

### 8.4 추가 제안: 번호 궁합 테스트 (Could, 장기 검토)
내 번호와 친구 번호(또는 오늘의 운세)를 비교해 "궁합 점수"를 보여주는 가벼운 바이럴 콘텐츠. 한국 소셜미디어에서 검증된 "테스트류" 포맷을 차용. 사행성과 무관한 순수 재미 요소. Phase 4 이후 우선 검토 후보.
