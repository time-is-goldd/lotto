# ROADMAP — 단계별 출시 로드맵 (Luck Platform 개정판)

> v2.0 개정. [[CRITICAL_REVIEW]]에서 지적된 "1인 개발자 현실과 불일치하는 MVP 범위" 문제를 해결하기 위해 전면 재작성한다. 프로젝트는 이제 '로또 사이트'가 아니라 **Luck Platform**이며, 로또는 그 첫 번째 서비스일 뿐이다 ([[MASTER_PRD]] §0 참조).
>
> **핵심 전제**: 이 로드맵은 팀이 아니라 1인 개발자를 기준으로 설계되었다. 확장성보다 "혼자 운영 가능한 현실성"을 우선한다.

---

## 0. MVP 재정의 원칙

기존 로드맵(v1.0)은 Phase 1에 로또 핵심기능 전체 + 꿈해몽 200건 + SEO + 관리자패널까지 8~10주 안에 몰아넣었다. 이는 1인 개발자에게 불가능한 범위였다. v2.0은 아래 원칙으로 MVP를 재정의한다.

1. **행운 다이어리가 핵심이지, 번호 생성이 핵심이 아니다.** MVP는 "번호를 뽑는 도구"가 아니라 "기록이 쌓이는 다이어리"를 최소 형태로 완성하는 것을 목표로 한다.
2. **콘텐츠 대량 생산(꿈해몽 200건 등)은 MVP 밖이다.** 최소 분량(20~30건)으로 시작해 출시 후 점진적으로 채운다.
3. **운영 자동화가 안 된 기능은 MVP에 넣지 않는다.** 매주 수동 반복 작업이 필요한 기능(배틀 수동 생성, 당첨번호 수동 대조 등)은 자동화 설계가 끝난 뒤에만 포함한다.
4. **커뮤니티·쇼핑몰·멤버십은 MVP가 아니다.** 이들은 사용자 기반이 생긴 뒤에 의미가 있는 기능이며, 초기에는 빈 게시판/빈 상점만 만드는 리스크가 크다.
5. **기능적 자동화와 인프라형 자동화를 구분한다(신규, 2026-08-05).** "당첨 자동 대조"처럼 반복 작업을 없애는 것(원칙 3)은 MVP에서도 필요하지만, 이를 구현하는 수단으로 Supabase Edge Functions·pg_cron 같은 별도 배치 인프라를 지금 도입할 필요는 없다. MVP는 관리자 액션이 트리거되는 시점에 Next.js API Route가 동기 처리하는 방식으로 동일한 자동화 효과를 낸다. Edge Function/Cron 인프라 자체는 실제 트래픽/자동화 요구가 커지는 Phase 5 이후에 도입한다([[IMPLEMENTATION_PLAN]] §4.3).

## 1. MVP 기능 분류 (MoSCoW)

### Must (반드시 있어야 함 — 없으면 서비스가 성립하지 않음)
| 기능 | 비고 |
|---|---|
| 카카오 로그인 | 가입 마찰 최소화, 전체 기능의 전제조건 |
| AI 번호 생성 (완전자동만) | 커스텀/고정번호 등 옵션은 제외, 최소 형태 |
| 번호 자동 저장 | 로그인 시 자동 저장 |
| **행운 다이어리 최소 버전** (히스토리 리스트 + 당첨확인) | 플랫폼의 정체성, [[FEATURE_SPEC]] §1 핵심기능 |
| 당첨 자동 확인 (관리자 수동 회차입력 기반) | 완전 자동 API 연동은 Should로 미룸, 입력은 수동이어도 대조는 자동 |
| 사이트 내 알림 | 당첨 결과 알림 최소 채널 |
| 카카오 공유 (번호 결과 1종) | 바이럴 최소 장치 |
| 기본 SEO 셋업 (sitemap, robots, 핵심 메타) | 검색 유입은 처음부터 시작되어야 함 |
| 이용약관/개인정보처리방침/19세 미만 이용제한 고지 | 법적 최소 요건 |

### Should (있으면 크게 좋아짐, 4~6주 내 여유 있으면 포함)
| 기능 | 비고 |
|---|---|
| 꿈 해몽 (최소 20~30건) + 꿈별 추천번호 | 콘텐츠는 최소 분량으로 시작 |
| AI 운세 번호 (간소화 버전: 종합운세+행운지수+추천번호만) | 10개 출력 전체가 아닌 축소판, [[FEATURE_SPEC]] §5 개정 참조 |
| 이메일 알림 | 무료 티어로 구현 가능 |
| 웹 푸시 알림 | 무료 구현 가능 |
| 행운 다이어리 캘린더 뷰 | 히스토리 리스트만 있는 최소버전에 이어 추가 |
| 실제 당첨 사례 (최소 큐레이션) | 신뢰도 확보용 최소 콘텐츠 |

### Could (여유 되면, 없어도 출시 가능)
| 기능 | 비고 |
|---|---|
| 친구 초대(레퍼럴) | Growth 장치지만 사용자 기반 없이는 효과 없음 |
| 로또 통계 페이지 | 정적 배치 콘텐츠, 후순위 가능 |
| 가이드/FAQ | 초기엔 최소 페이지 3~5개로 축소 가능 |
| 로또 명당(판매점) 콘텐츠 | SEO 기회는 크지만 데이터 정비 시간 필요 |

### Won't (이번 범위에서 명시적으로 제외)
| 기능 | 사유 |
|---|---|
| 이번주 배틀 | 정기 운영 자동화가 되기 전까지 보류 ([[ADMIN_REQUIREMENTS]] 자동화 설계 완료 후 Phase 4) |
| 명예의 전당 | 사용자/데이터가 쌓이기 전엔 빈 화면일 뿐 |
| 커뮤니티 게시판 | 콜드스타트 리스크 큼, Phase 4로 이동 |
| 쇼핑몰 | Phase 5 |
| 멤버십(구독) | Phase 7 |
| 카카오 알림톡 | 사업자등록 필요, Phase 2 이후 |
| 실시간 번호 생성 로그 | 인프라 대비 가치가 낮음, Phase 3 이후 재검토 |

> MVP 목표 기간: **4~6주** (1인 개발 기준). 이 표가 [[FEATURE_SPEC]]의 모든 기능 항목에 그대로 태깅된다.

## 2. Phase별 로드맵

### Phase 0 — 기획 (완료 예정, 현재 단계)
- 설계 문서 15종 확정 (본 개정 작업 포함)
- Supabase 프로젝트 셋업, 카카오 비즈니스 앱 등록/심사 신청
- 최소 꿈해몽 콘텐츠 20~30건 사전 작성

**산출물**: 승인된 설계 문서, Supabase 프로젝트, 콘텐츠 시드

### Phase 1 — MVP (4~6주)
§1의 Must + 여유 있는 Should 항목까지 포함해 출시. 목표는 "행운 다이어리가 작동하는 최소 로또 서비스"를 시장에 내놓는 것.

**성공 기준**: 첫 가입자 확보, 당첨 자동확인 배치가 실제 회차에서 오류 없이 동작, 핵심 키워드 색인 시작

### Phase 2 — 회원 기능 강화 (MVP 이후 +3~4주)
- 이메일/웹푸시 알림 정식 적용
- 행운 다이어리에 "구매여부/구매금액/생성이유/행운메모" 필드 추가 ([[FEATURE_SPEC]] §행운다이어리)
- 카카오 공유 콘텐츠 확장(운세 결과 공유)
- 프로필/설정 페이지 완성

### Phase 3 — 행운 다이어리 고도화 (+4주)
- 월간/연간 리포트 뷰
- **연말 Luck Report 자동 생성** (Spotify Wrapped 스타일, [[FEATURE_SPEC]] 참조)
- 행운 캘린더 완성형(꿈기록/운세기록 통합 뷰)
- 개인 통계(가장 많이 생성한 번호, 최고 당첨 기록)

### Phase 4 — 커뮤니티 (+4~6주)
- 게시판 오픈 (운영팀 시드 게시글로 콜드스타트 대응, [[CONTENT_STRATEGY]])
- 친구 초대(레퍼럴) 시스템
- 친구와 배틀 / 친구 랭킹
- 이번주 배틀 (자동화된 생성/정산 워크플로 완성 후)
- 명예의 전당

### Phase 5 — 쇼핑몰 (+4주)
- 행운 상품(부적/굿즈/기념품) 카탈로그 + 결제 연동
- 연말 Luck Report의 유료 옵션(고급 PDF 등) 연계 판매

### Phase 6 — 입점 (파트너 확장, +4~6주)
- 제3자 판매자 입점 구조 (products.seller_id 등 [[DATABASE_SCHEMA]] 확장 필드 활용)
- 제휴 마케팅 링크/추적 (affiliate_links)

### Phase 7 — 멤버십 (+3~4주)
- 프리미엄 구독(광고 제거, AI 운세 상세판, 배틀 우선참여권 등)
- 등급별 뱃지/혜택 체계

### Phase 8 — AI 자동화 운영 고도화 (지속)
- 당첨번호 자동 수집(공공데이터 API) + 관리자 승인 워크플로
- 꿈해몽/당첨사례 콘텐츠 AI 초안 생성 파이프라인
- 커뮤니티 신고/스팸 AI 필터링 고도화
- 운영 대시보드 자동 리포트(주간 운영 요약 자동 생성)

## 4. 우선순위 판단 원칙 (개정)

기능 추가/보류 논의 시 아래 순서로 판단한다:
1. **자동화 가능한가?** 반복 수동작업이 필요하면 자동화 설계 없이는 채택하지 않는다 ([[ADMIN_REQUIREMENTS]] 원칙).
2. **행운 다이어리 재방문에 기여하는가?** North Star Metric은 여전히 멀티기능 사용률이지만, 다이어리가 그 중심 허브다 ([[MASTER_PRD]]).
3. **1인 운영으로 유지보수 가능한가?** 인프라/운영 부담이 큰 기능은 후순위.
4. **SEO 유입에 즉시 기여하는가?** 콘텐츠형 기능은 조기 확보를 우선한다.

## 5. 리스크 기반 일정 버퍼

각 Phase 종료 시 1주 버퍼를 두고 (1) 법무/정책 재검토, (2) 실제 운영 부하 점검(반복작업 발생 여부 확인 후 자동화 여부 재결정)을 수행한다.
