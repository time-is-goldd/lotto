# AI ENGINEERING CONSTITUTION — 프로젝트 헌법

> 버전 1.0 · 이 문서는 Luck Platform의 **최상위 규칙**이다. [[MASTER_PRD]], [[ROADMAP]], [[FEATURE_SPEC]], [[EXECUTION_PLAN]]을 포함한 모든 설계 문서와 모든 코드 작업은 이 문서와 충돌할 수 없다. 새 기능, 새 문서, 새 리팩토링 — 그 무엇이든 이 헌법을 위반하면 안 된다.

## 0. 이 문서의 지위

- 이 문서는 "빠른 개발"보다 "절대 무너지지 않는 구조"를 우선한다는 것을 전제로 존재한다. 이 프로젝트는 1인 개발자가 Claude Code와 함께 **수년간** 유지보수할 플랫폼이며, 지금의 편의가 3년 뒤의 부채가 되는 것을 막는 것이 이 문서의 존재 이유다.
- 다른 설계 문서(예: [[FEATURE_SPEC]])가 이 헌법과 충돌하는 내용을 담고 있다면, **이 헌법이 우선**하며 해당 설계 문서를 수정해야 한다.
- 이 문서 자체는 AI가 임의로 수정하지 않는다. 사용자가 명시적으로 개정을 요청할 때만 변경한다.
- 새로운 기능 요청이 이 헌법과 충돌할 경우, AI(Claude Code)는 구현을 시작하기 전에 반드시 충돌 사실을 사용자에게 알리고 확인받는다. 조용히 헌법을 어기고 구현부터 하지 않는다.

## 1. 프로젝트 철학

이 프로젝트는 로또 번호 생성기가 아니라 **Luck Platform** — 행운을 기록하고, 관리하고, 공유하는 플랫폼이다 ([[MASTER_PRD]] §0). 로또는 이 플랫폼이 시장에 내놓은 첫 번째 서비스일 뿐이며, 꿈해몽·운세·통계·커뮤니티·쇼핑몰·멤버십·파트너까지 이어지는 더 큰 구조의 한 조각이다.

이 철학이 실무에 갖는 의미는 다음과 같다:

- **로또만을 위한 설계를 하지 않는다.** 어떤 기능을 만들 때든 "이것이 다른 브랜치(운세, 꿈, 커뮤니티 등)에서도 재사용되거나 확장될 수 있는가"를 먼저 검토한다.
- **행운 다이어리가 플랫폼의 중심이다.** 어떤 새 기능도 결국 사용자의 기록이 쌓이는 곳(행운 다이어리)과 연결되어야 하며, 다이어리와 무관하게 고립된 기능은 만들지 않는다.
- **플랫폼 전체를 항상 고려한다.** 당장 로또 기능만 손보더라도, 그 결정이 향후 Dream/Fortune/Community/Shop/Membership/Partners 브랜치에 어떤 전제를 강요하게 되는지 항상 염두에 둔다.

## 2. 개발 원칙

아래 10가지 원칙은 모든 기술적 의사결정의 기준이다. 두 원칙이 충돌할 때는 **단순함 > 유지보수 > 보안/데이터무결성 > 접근성 > 성능/SEO/모바일 > 재사용 > 자동화** 순서로 우선순위를 판단한다(단, 보안과 데이터 무결성은 사실상 타협 대상이 아니다).

| 원칙 | 왜 필요한가 |
|---|---|
| **단순함 우선** | 1인 개발자에게는 복잡성을 나눠질 동료가 없다. 복잡한 구조는 만들 때는 그럴듯해 보여도, 반년 뒤 본인조차 이해하지 못하는 코드가 된다. 가장 단순한 해법이 항상 기본값이다. |
| **재사용 우선** | 같은 문제를 두 번 다른 방식으로 풀면 유지보수 지점이 두 배가 된다. [[DESIGN_SYSTEM]]과 기존 컴포넌트/함수를 먼저 찾고, 없을 때만 새로 만든다. |
| **유지보수 우선** | 이 프로젝트는 "수년간" 운영된다. 코드는 작성되는 순간보다 읽히고 수정되는 시간이 압도적으로 길다. 지금 5분 빨리 끝내는 방법보다 6개월 뒤에도 이해 가능한 방법을 택한다. |
| **성능 우선** | 성능은 [[SEO_STRATEGY]]의 Core Web Vitals 순위 요인이자, 시니어 사용자의 낮은 사양 기기·느린 네트워크 환경에서도 서비스가 동작하게 만드는 접근성 문제이기도 하다. |
| **접근성 우선** | 40~70대가 핵심 타겟이다([[UI_UX_GUIDELINE]]). 접근성은 옵션이 아니라 이 서비스가 존재하는 이유의 일부다. |
| **SEO 우선** | 1인 개발자는 광고 예산으로 트래픽을 살 수 없다. 유기적 검색 유입이 사실상 유일한 성장 채널이므로([[SEO_STRATEGY]]), 모든 페이지는 태생적으로 SEO를 고려해 설계된다. |
| **모바일 우선** | 실사용 트래픽의 대다수가 모바일이며, 카카오톡 인앱 브라우저 유입이 큰 비중을 차지한다([[USER_FLOW]] §5). 데스크톱은 모바일 설계의 확장판으로 다룬다. |
| **자동화 우선** | 1인 개발자에게 반복 수동 작업은 곧 번아웃과 서비스 방치로 이어진다([[MASTER_PRD]] §3, [[ADMIN_REQUIREMENTS]]). 자동화되지 않은 반복 작업은 기술 부채로 취급한다. |
| **보안 우선** | 생년월일·성별 등 개인정보를 다루고, 사고를 잡아줄 동료 리뷰어가 없다. RLS·환경변수 관리 실수 하나가 전체 사용자 데이터 유출로 이어질 수 있다([[CRITICAL_REVIEW]] D-01 사례). |
| **데이터 무결성 우선** | 당첨 확인 로직이 틀리면 이 서비스의 신뢰는 그 순간 끝난다. 행운 다이어리에 잘못된 기록이 남는 것은 기능 버그가 아니라 신뢰 붕괴 사건이다. |

## 3. 코드 작성 원칙

### 절대 금지
- **중복 코드 작성 금지**: 동일하거나 유사한 로직이 2곳 이상에 존재하면 안 된다. 발견 즉시 공통 함수/컴포넌트로 추출한다.
- **하드코딩 금지**: 매직넘버, 매직스트링을 코드에 직접 쓰지 않는다. `lib/constants/`에 정의하고 참조한다. (예: 번호 범위 1~45, 등수 판정 기준 등)
- **`any` 사용 최소화**: 불가피한 경우가 아니면 사용하지 않는다. 특히 Supabase에서 생성된 DB 타입(`lib/types/database.ts`, [[EXECUTION_PLAN]] Phase1)을 항상 우선 사용한다.
- **의미 없는 주석 금지**: 코드가 "무엇을" 하는지 설명하는 주석은 쓰지 않는다(좋은 이름이 대신한다). "왜" 그렇게 했는지(숨은 제약, 버그 회피, 법적/정책적 이유)만 남긴다.
- **사용하지 않는 코드 방치 금지**: 죽은 코드(dead code), 주석 처리된 코드 블록, 도달 불가능한 분기는 발견 즉시 삭제한다. "혹시 몰라서" 남겨두지 않는다 — Git 히스토리가 백업이다.
- **사용하지 않는 라이브러리 설치 금지**: 라이브러리 추가는 반드시 "왜 직접 구현하지 않고 이 라이브러리가 필요한가"를 먼저 답할 수 있어야 한다.

### 추가 규칙
- **함수는 하나의 책임만 가진다**: 특히 `lib/logic/*`의 순수 함수(`generateNumbers`, `matchNumbers` 등)는 부수효과 없이 입력→출력만 담당한다([[EXECUTION_PLAN]] Phase5~6).
- **매직넘버 대신 이름 있는 상수**: 등수 판정 기준(5개+보너스=2등 등), 페이지네이션 크기 등은 전부 상수화한다.
- **서버/클라이언트 경계를 명확히 구분한다**: `SUPABASE_SERVICE_ROLE_KEY`를 사용하는 코드는 서버 전용 파일에만 존재해야 하며, 클라이언트 번들에 포함되지 않는지 매번 확인한다([[IMPLEMENTATION_PLAN]] §5).
- **타입은 DB 스키마에서 파생한다**: `profiles`, `user_numbers` 등의 타입을 손으로 재정의하지 않고 `supabase gen types`로 생성된 타입을 단일 진실 공급원(Single Source of Truth)으로 삼는다.
- **에러를 조용히 삼키지 않는다**: `catch` 블록에서 아무 처리 없이 무시하는 코드를 작성하지 않는다. 최소한 로깅하거나 사용자에게 실패를 알린다.
- **새 코드를 쓰기 전 기존 코드를 검색한다**: 유사 컴포넌트/함수가 이미 있는지 먼저 확인하지 않고 새로 만드는 것을 금지한다(§2 재사용 우선의 실행 규칙).
- **폴더 구조를 임의로 바꾸지 않는다**: [[EXECUTION_PLAN]] 부록 A의 폴더 구조를 따른다. 구조 변경이 필요하면 별도로 사용자 승인을 받는다.

## 4. AI 작업 규칙 (Task Execution Protocol)

Claude Code는 **절대로 한 번에 많은 기능을 만들지 않는다.** 모든 작업(Task)은 예외 없이 아래 7단계 **Task Execution Protocol**을 따른다. 목표는 "작업 후 문제 발견"이 아니라 "작업 전 문제 예방"이다 — 1인 개발자에게는 사후에 문제를 잡아줄 동료 리뷰어가 없으므로, 사전 분석이 사실상 유일한 안전망이다.

```
Phase A. Pre-change Analysis → Phase B. Implementation → Phase C. Validation
   → Phase D. Self Review → Phase E. Documentation Update → Phase F. Git Commit
   → Phase G. Final Task Report
```

### Phase A. Pre-change Analysis (작업 전 분석)

구현(Phase B)에 들어가기 전, 반드시 아래 6개 항목을 정리한다. 정리되기 전에는 구현을 시작하지 않는다.

1. **Task 목표**: 이번 작업이 정확히 무엇을 달성하는지 한 문단으로 정리한다.
2. **현재 프로젝트 상태 확인**: [[EXECUTION_PLAN]] 부록 B에서 지금이 어느 Phase/Task이고 직전 Task가 무슨 상태를 남겼는지 확인한다.
3. **관련 문서 확인** — 최소한 아래를 확인한다: [[MASTER_PRD]], [[EXECUTION_PLAN]], 본 헌법, 관련 [[FEATURE_SPEC]] 항목. 이 과정에서 설계 문서나 이 헌법과 충돌하는 지점을 발견하면, 구현에 앞서 반드시 사용자에게 먼저 알린다.
4. **영향 분석**: 기존 페이지, 기존 컴포넌트, DB, API, SEO, 성능, 보안에 실제 영향이 있는지 확인한다.
5. **구현 계획**: 생성 파일, 수정 파일, 삭제 파일, 라이브러리 변경 여부, Migration 필요 여부를 명시한다.
6. **리스크 평가**: Critical / High / Medium / Low로 분류한다.

큰 단위(Phase 전체)의 착수 시점에는 이 분석이 [[EXECUTION_PLAN]]의 "Design Gate"로, 개별 Task 단위에서는 이 Phase A로 수행된다 — 규모만 다를 뿐 같은 원칙이다.

### Phase B. Implementation

- 한 번에 하나의 Task만 수행한다. 여러 작업을 하나의 세션/커밋에 뒤섞지 않는다.
- Phase A에서 승인된 범위만 구현한다. 사용자가 명시적으로 요청하지 않은 범위 확장(부탁받지 않은 리팩토링, 새 문서 생성 등, §15 참조)을 임의로 하지 않는다.
- 필요 없는 기능을 추가하지 않는다.
- 기존 코드·컴포넌트 재사용을 우선한다(§2, §3).
- 새 라이브러리는 "왜 필요한가"를 먼저 기록한 뒤에만 추가한다(§3).

### Phase C. Validation

구현 완료 후 반드시 실행하고 결과를 기록한다. 결과를 기록하지 않은 작업은 검증되지 않은 것으로 간주한다.

- **필수**: `npm run lint`, `npm run type-check`, `npm test`, `npm run build`
- **조건부 필수**: 이번 Task가 UI/페이지에 영향을 준다면 Lighthouse·모바일·접근성 검사가 §9 테스트 규칙에 따라 **필수**가 된다("필요 시"는 생략 가능하다는 뜻이 아니라, UI 변경 여부로 적용 대상이 갈린다는 뜻이다). DB/보안에 영향을 준다면 각각 §7, §11 기준으로 점검한다. Bundle 분석은 의존성이 추가되었을 때 수행한다.

### Phase D. Self Review

AI는 이 단계에서 구현자가 아니라 **리뷰어(Reviewer)** 관점으로 전환해 자신이 작성한 코드를 다시 검토한다. 확인 대상: 중복 코드, 과도한 추상화, 불필요한 파일, 기술 부채, 성능 문제, 보안 문제, UX 문제. 문제가 발견되면 Phase F(커밋) 이전에 먼저 리팩토링한다.

### Phase E. Documentation Update

변경에 실제로 영향을 받는 문서만 수정한다. 관련 없는 문서는 손대지 않는다.

| 변경 내용 | 갱신 대상 |
|---|---|
| DB 변경 | [[DATABASE_SCHEMA]] |
| 기능 변경 | [[FEATURE_SPEC]] |
| 개발 순서 변경 | [[EXECUTION_PLAN]] |
| SEO 변경 | [[SEO_STRATEGY]] |

동작이 바뀌었는데 문서를 갱신하지 않은 작업은 미완료로 간주하며, [[EXECUTION_PLAN]] 부록 B 진행 추적표도 함께 갱신한다.

### Phase F. Git Commit

커밋 전 확인: 테스트 통과 여부, 변경사항(diff) 재확인, 민감정보(개인정보·비밀키) 포함 여부(§11). 커밋 메시지는 §8.2 형식(`type: description`, 예: `feat:`/`fix:`/`refactor:`/`docs:`/`chore:`)을 따른다.

### Phase G. Final Task Report

모든 Task 종료 시 아래 형식으로 보고한다. **보고 후에는 다음 Task를 구현하지 않고 멈춘다.**

```
# TASK REPORT
1. 완료 항목
2. 생성 파일
3. 수정 파일
4. 삭제 파일
5. 설치 라이브러리
6. Validation 결과 (lint / type-check / test / build)
7. Impact Analysis
8. Technical Debt
9. Risk
10. 다음 Task 추천
```

## 5. 기능 추가 원칙

새 기능을 만들기 전, 반드시 아래 질문에 답한다. 질문은 두 계층으로 나뉜다.

### 5.1 하드 게이트 (모두 통과해야 함 — 하나라도 실패하면 설계를 다시 검토한다)
- 기존 기능으로 해결 가능한가? (아니라면 왜 불가능한지 명확히 설명 가능한가)
- 기존 컴포넌트를 재사용할 수 있는가? (검토 없이 새로 만들지 않았는가)
- 새로운 DB 테이블이 정말 필요한가? (기존 테이블 확장으로 안 되는가, [[DATABASE_SCHEMA]] §7 원칙)
- 새로운 API가 정말 필요한가? (기존 API의 파라미터 확장으로 안 되는가)
- 혼자 유지보수 가능한가? (별도 인프라, 별도 운영 인력을 가정하지 않는가, [[MASTER_PRD]] §3)

### 5.2 가치 게이트 (아래 중 최소 1개 이상 "예"여야 함)
- SEO 유입에 도움이 되는가?
- 재방문율이 증가하는가?
- 회원가입률이 증가하는가?
- 수익화와 연결되는가?

가치 게이트를 하나도 만족하지 못하는 기능은 "재미있어 보인다"는 이유만으로 만들지 않는다. §14 프로젝트 KPI와 직접 연결된다.

## 6. UI 원칙

40~70대 사용자가 **3초 안에** 원하는 기능을 찾을 수 있어야 한다([[INFORMATION_ARCHITECTURE]] §6 3초 법칙). 모든 페이지는 아래 세 가지를 다른 무엇보다 우선한다.

1. **접근성**: 터치 타겟 44px 이상, 본문 16px 이상, WCAG AA 대비율 준수([[UI_UX_GUIDELINE]]).
2. **가독성**: 짧은 문장, 쉬운 단어, 충분한 행간. 전문용어·한자어 최소화.
3. **명확성**: 화면당 핵심 행동은 하나. 선택지는 항상 2~3개로 제한. 아이콘 단독 사용 금지(텍스트 라벨 동반).

새 화면을 만들 때마다 [[DESIGN_SYSTEM]]의 토큰과 컴포넌트를 사용하며, 임의의 색상값·폰트크기·간격값을 직접 지정하지 않는다.

## 7. DB 원칙

**새로운 테이블은 정말 필요한 경우에만 생성한다.** 기존 테이블에 컬럼을 추가하는 것으로 해결되는지 항상 먼저 검토한다([[DATABASE_SCHEMA]] §7).

- **정규화**: 기본은 3정규형을 따른다. 단, 조회 성능이 중요한 통계·요약 데이터(예: `user_period_stats`, 사이트 전체 통계 캐시)는 의도적으로 비정규화할 수 있다 — 단, 왜 비정규화했는지 마이그레이션 파일 주석 또는 [[DATABASE_SCHEMA]]에 반드시 기록한다.
- **RLS**: 모든 신규 테이블은 생성과 동시에 RLS를 활성화한다. RLS 정책이 없는 테이블은 머지하지 않는다([[DATABASE_SCHEMA]] §6). 공개 테이블(예: `draws`, `dreams`)만 명시적으로 전체 SELECT를 허용하는 화이트리스트 방식을 따른다.
- **Index**: 실제 조회 패턴이 확정된 뒤에 추가한다(조기 최적화 금지). 단, 외래키(FK) 컬럼에는 기본적으로 인덱스를 건다.
- **Timestamp 트리거**: `updated_at`이 필요한 테이블은 전용 트리거 함수를 새로 만들지 않고, 공용 함수(`public.set_updated_at()`, `0001`에서 최초 정의)를 재사용하는 트리거만 추가한다(§3 "중복 코드 작성 금지"의 DB 적용).
- **FK 삭제 정책**: FK의 `ON DELETE`는 명시적 근거가 없다면 Postgres 기본값(`NO ACTION`)을 쓴다. `CASCADE`/`SET NULL`이 필요한 예외(부모 없이 의미 없는 자식 행, 콘텐츠 삭제와 무관하게 보존돼야 하는 개인 기록 등)는 반드시 [[DATABASE_SCHEMA]]에 근거를 남긴다([[DATABASE_SCHEMA]] §3.0 예시 참조).
- **Storage**: 새 업로드 기능을 추가하기 전에 버킷별 접근 정책, 용량 제한, 허용 파일 타입을 먼저 정의한다([[DATABASE_SCHEMA]] §5). 정책 없는 업로드 기능은 만들지 않는다.
- **Migration**: 모든 schema 변경은 **Supabase CLI로 migration 파일을 생성한 뒤 적용**한다. Dashboard SQL Editor에서 직접 스키마를 수정하는 것은 긴급 상황 확인 용도로만 허용하며, 확인 후에는 동일한 변경을 반드시 migration 파일로 재현해 커밋한다. 마이그레이션 파일은 순번으로 관리하고, 이미 적용된(운영에 반영된) 마이그레이션 파일은 절대 수정하지 않는다 — 항상 새 파일을 추가한다([[DATABASE_SCHEMA]] §10, [[EXECUTION_PLAN]] Phase1 §9).
- **Rollback**: 모든 마이그레이션은 되돌릴 수 있는 경로를 함께 고려한다. `DROP TABLE`, `DROP COLUMN` 등 비가역적 작업은 실행 전 반드시 사용자 승인을 받고, 가능하면 컬럼을 즉시 삭제하지 않고 일정 기간 사용 중단(deprecated) 상태로 둔다.

## 8. Git 규칙

1인 개발이지만, 향후 팀이 합류해도 그대로 유지 가능한 수준으로 규칙을 정한다.

### 8.1 브랜치 전략
- `main`: 항상 배포 가능한 상태를 유지한다(Vercel 프로덕션과 연결).
- `feat/<기능명>`, `fix/<버그명>`, `chore/<작업명>`: 작업 단위별 브랜치. 무거운 GitFlow 대신 단순한 GitHub Flow를 따른다(1인 개발에 불필요한 오버헤드를 만들지 않기 위함, §2 단순함 우선).
- 브랜치는 병합 후 삭제한다.

### 8.2 Commit 규칙
Conventional Commits 형식을 따른다: `type: 설명`
- `feat:` 신규 기능, `fix:` 버그 수정, `refactor:` 동작 변화 없는 구조 개선, `docs:` 문서 변경, `chore:` 빌드/설정 변경, `test:` 테스트 추가/수정
- 이유: 나중에 변경 이력을 추적하거나 CHANGELOG을 자동 생성할 수 있고, 팀원이 합류했을 때 관례를 설명할 필요가 없다.
- 한 커밋에는 하나의 논리적 변경만 담는다([[AI_ENGINEERING_CONSTITUTION]] §4와 동일한 원칙의 Git 적용).

### 8.3 PR 규칙
- 1인 개발이라도 `main`에 직접 push하지 않고 PR을 통해 self-review(diff 재검토)를 거친다.
- Vercel Preview Deployment로 실제 동작을 확인한 뒤에만 머지한다.
- PR 설명에 "이 변경이 §14 KPI 중 무엇을 개선하는가"를 한 줄로 남긴다(§5 가치 게이트와 연결).

### 8.4 릴리즈 규칙
- [[EXECUTION_PLAN]]의 각 Phase 완료 시점마다 Git 태그를 남긴다(예: `v0.1.0-phase6`).
- 릴리즈 노트에는 무엇이 새로 동작하게 됐는지 사용자 관점에서 기록한다.

### 8.5 버전 규칙
시맨틱 버저닝(`major.minor.patch`)을 따른다.
- `major`: 기존 사용자 데이터/URL 구조에 영향을 주는 큰 변경([[SITEMAP]] 구조 변경 등)
- `minor`: 새로운 기능 추가(하위 호환 유지)
- `patch`: 버그 수정, 문서 수정, 사소한 UI 조정

## 11. 보안 원칙

OWASP Top 10을 기준으로 아래를 기본 원칙으로 삼는다.

- **Auth**: 카카오/이메일 로그인 모두 Supabase Auth 세션으로 통일 관리한다([[IMPLEMENTATION_PLAN]] §2~3). 세션 토큰을 로컬스토리지에 직접 다루지 않고 Supabase SDK/쿠키 관리에 위임한다.
- **RLS**: 모든 테이블 기본 활성화가 원칙이다([[DATABASE_SCHEMA]] §6). RLS를 우회하는 `service_role` 클라이언트는 서버 전용 코드에서만, 그것도 반드시 필요한 최소 범위(관리자 작업, 배치)에만 사용한다.
- **환경변수**: 비밀키는 `NEXT_PUBLIC_` 접두사를 붙이지 않는다. `.env.local`은 커밋하지 않는다. 프로덕션 환경변수는 Vercel 대시보드에서만 관리한다.
- **API**: 모든 API 라우트는 입력값 검증(스키마 검증)을 거친다. 인증이 필요한 API는 요청마다 세션을 재확인하고, 프론트엔드의 권한 체크만 믿지 않는다(서버가 최종 방어선).
- **업로드**: Storage 버킷별로 파일 크기·타입 제한을 강제한다([[DATABASE_SCHEMA]] §5). 사용자 업로드 파일은 원본 파일명을 그대로 신뢰하지 않고 서버에서 이름을 재생성한다.
- **XSS**: 사용자 입력(커뮤니티 게시글, 닉네임, 꿈 기록 등)은 렌더링 전 반드시 sanitize한다. `dangerouslySetInnerHTML` 류의 사용은 원칙적으로 금지하고, 불가피할 때만 sanitize 라이브러리를 거친 값에 한해 허용한다.
- **CSRF**: 상태 변경 요청(POST/PUT/DELETE)은 Supabase/Next.js의 기본 CSRF 보호 메커니즘을 우회하지 않는다.
- **Rate Limit**: 로그인 시도, 게시글 작성, 번호 생성 API 등 남용 가능한 엔드포인트에는 요청 빈도 제한을 둔다([[IMPLEMENTATION_PLAN]] §5, 특히 신규 가입 계정의 초기 24시간 게시글 작성 제한 등).
- **개인정보 최소 수집**: 생년월일·성별 등은 목적(운세 계산)에 필요한 범위에서만 수집하고, 로그/에러 메시지/커밋 메시지에 절대 노출하지 않는다.

## 12. SEO 원칙

모든 페이지는 예외 없이 SEO를 고려해 제작한다([[SEO_STRATEGY]]). 신규 페이지 배포 전 아래 체크리스트를 통과해야 한다.

- [ ] 고유한 `Title` (페이지마다 중복 없음, 핵심 키워드 포함)
- [ ] 고유한 `Description` (요약 + 행동유도)
- [ ] `Heading` 구조가 논리적(H1 하나, H2/H3 계층 준수)
- [ ] 해당 콘텐츠 유형에 맞는 `Schema`(JSON-LD) 적용 ([[SEO_STRATEGY]] §4)
- [ ] `Open Graph` 태그(카카오 공유 미리보기 대응 포함)
- [ ] `Canonical` URL 명시(중복 콘텐츠 방지)
- [ ] 관련 콘텐츠로의 `Internal Link` 최소 1개 이상
- [ ] 3depth 이상 페이지는 `Breadcrumb` 노출 + JSON-LD
- [ ] `Sitemap`에 포함 여부 판단(공개 콘텐츠는 포함, 개인화 페이지는 제외)
- [ ] `robots` 메타(개인화/관리자 페이지는 `noindex, nofollow`)

## 13. 운영 원칙

운영자(1인)가 반복하는 작업은 언젠가 반드시 자동화하고, 최종적으로는 AI가 대신 처리하도록 설계한다([[ADMIN_REQUIREMENTS]] §10). 발전 단계는 다음과 같다.

```
1단계: 수동 운영   — 사람이 매번 직접 처리 (예: 회차 결과 수동 입력)
2단계: 자동화      — 정해진 규칙대로 시스템이 처리, 사람은 승인만 (예: API 자동수집 + 승인 클릭)
3단계: AI 운영      — AI가 판단까지 포함해 초안/의사결정을 제시, 사람은 예외만 처리 (예: AI 콘텐츠 초안 생성 + 이상 게시글 판단)
```

새로운 반복 작업이 생기면, 그 즉시 "이 작업이 지금 몇 단계인가"를 표시하고 다음 단계로 끌어올릴 계획을 [[ADMIN_REQUIREMENTS]] §10 표에 추가한다. 자동화 경로가 없는 반복 작업은 원칙적으로 신규 기능 승인 대상에서 보류한다(§5 하드 게이트 "혼자 유지보수 가능한가"와 직결).

어떤 KPI도 개선하지 못하는 기능은 "재미있다", "있으면 좋을 것 같다"는 이유만으로는 채택하지 않는다(§5.2 가치 게이트와 동일한 판단 축).

## 15. AI가 절대로 하면 안 되는 것

아래 행동은 프로젝트를 서서히 혹은 즉시 무너뜨릴 수 있으므로, Claude Code는 어떤 상황에서도 이를 하지 않는다.

1. 무분별한 라이브러리 추가 (§3 "사용하지 않는 라이브러리 설치 금지" 위반)
2. 기존 컴포넌트/함수를 검색하지 않고 유사한 중복 컴포넌트 생성
3. 매직넘버·매직스트링 하드코딩
4. 기존에 동작하던 기능을 깨뜨리는 수정을 테스트 없이 배포
5. 요청받지 않은 불필요한 리팩토링 진행
6. 기능 구현 후 관련 설계 문서를 갱신하지 않고 방치
7. RLS 정책 없이 새 테이블 생성
8. `service_role` 키 또는 기타 비밀키를 클라이언트 코드/공개 저장소에 노출
9. 이미 적용된 마이그레이션 파일을 수정
10. 사용자 승인 없이 프로덕션 데이터베이스에 직접 DDL/DML 실행
11. 사용자 승인 없이 `git push --force` 또는 히스토리 재작성
12. 여러 개의 서로 다른 기능을 하나의 커밋/PR에 몰아넣기
13. 실패하는 테스트나 타입 에러를 무시한 채 "완료"로 보고
14. 임시방편(quick fix, 땜질)을 정식 해결책인 것처럼 보고
15. 에러를 조용히 삼키는 코드(silent catch) 작성
16. 사용자의 개인정보(생년월일, 이메일 등)를 로그·커밋 메시지·주석에 노출
17. 헌법이나 설계 문서와 상충하는 기능을 조용히 구현(사전 고지 없이)
18. 당첨 매칭, 등수 판정 등 핵심 로직을 테스트 없이 수정
19. "빠른 구현"을 이유로 접근성 원칙(§6)을 생략
20. [[MASTER_PRD]] 비목표를 위반하는 현금성 보상·사행성 조장 문구·기능을 임의로 추가
21. 지금 필요하지 않은 인프라(별도 서버, 마이크로서비스, Redis 등)를 "확장성을 위해" 미리 도입
22. 배포 전 Lighthouse/접근성 체크를 생략하고 완료 보고
23. 영향 범위를 확인하지 않고 여러 화면이 공유하는 컴포넌트를 수정
24. 사용자 지시 없이 새로운 최상위 설계 문서를 임의로 생성해 문서 체계를 어지럽힘
25. 하나의 세션/작업 단위에서 여러 Phase([[EXECUTION_PLAN]])에 걸친 작업을 동시에 진행
26. 신규 기능 추가 시 §5 기능 추가 원칙의 게이트 검토를 생략

## 16. 문서 간 관계 요약

```
AI_ENGINEERING_CONSTITUTION (본 문서, 최상위 — 모든 것의 상위 규칙)
        │
        ├── MASTER_PRD (비전/목표/비목표)
        ├── ROADMAP / EXECUTION_PLAN (무엇을 언제, 어떤 순서로)
        ├── FEATURE_SPEC / DATABASE_SCHEMA / SITEMAP / IA (무엇을 어떻게)
        ├── UI_UX_GUIDELINE / DESIGN_SYSTEM (화면을 어떻게)
        ├── SEO_STRATEGY / CONTENT_STRATEGY (유입을 어떻게)
        ├── ADMIN_REQUIREMENTS / IMPLEMENTATION_PLAN (운영/기술을 어떻게)
        └── CRITICAL_REVIEW (과거 실수 기록 — 반복 방지 근거)
```

새 기능을 검토할 때는 이 순서로 문서를 확인한다: **본 헌법 → MASTER_PRD → EXECUTION_PLAN(현재 Phase) → 해당 영역 설계 문서.**
