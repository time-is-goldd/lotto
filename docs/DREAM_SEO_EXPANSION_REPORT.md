# Phase10-9 — Dream SEO Content Expansion

목표: Luck Platform 꿈해몽을 "25개 대표 꿈 + 101개 세부 상황"의 작은 기능에서, 한국어 꿈
검색어에 지속적으로 대응할 수 있는 콘텐츠 자산으로 확장한다. 단순 페이지 수 증가가 아니라,
사용자가 구체적인 꿈 검색어로 들어왔을 때 그 페이지 하나만 읽어도 궁금증이 해소되는 것이
목표다.

## 1. SEO 목표 (재확인)

검색 노출/상위 노출을 보장한다고 주장하지 않는다. 이번 Task는 검색 노출 가능성을 높이기 위한
콘텐츠·정보구조 확장이며, 최종 성공 기준은 페이지 수가 아니라 각 페이지의 독립적인 정보
만족도다.

## 2. Keyword Research 방법

실제 한국어 꿈해몽 사이트(사주플러스, 별담, 홍심당, 몽담, 운명공학 등)를 웹 검색으로 조사해
구조/분류 방식을 확인했다. 본문 문장은 전혀 베끼지 않고 "어떤 상황을 다루는지, 어떻게
분류하는지"만 참고했다. 상세 내용은 `docs/DREAM_SEO_CONTENT_MAP.md` §1 참조.

## 3. Search Intent Map

`docs/DREAM_SEO_CONTENT_MAP.md` §2에 대분류(동물/신체/인물/돈/자연/공포/생활/교통)별로
기존 커버 항목·신규 편입 항목·다음 Wave 후보를 표로 정리했다. 지시문이 예시로 준 목록을
그대로 확정하지 않고, 실제 조사와 기존 콘텐츠 근접도를 근거로 재분류했다.

## 11. Parent Hub 콘텐츠 모델 및 구현

**새 column/table을 추가하지 않았다**(지시문 §12). 기존 `dreams.interpretation`(TEXT) 안에
`## 소제목` 줄을 포함시키는 경량 마크다운 규칙을 도입했다.

- `components/dream/DreamHubContent.tsx`(신규): `interpretation`을 줄 단위로 파싱해 `##
  ` 로 시작하는 줄은 실제 `<h2>`로(지시문 §17 "단순 CSS heading div로 처리하지 않는다"),
  나머지는 문단(`<p>`)으로 렌더링한다. `##`가 전혀 없으면(기존 25개 레거시 Parent) 지금과
  동일하게 한 문단으로 렌더링된다 — 하위 호환을 실측으로 확인했다(§25 로컬 dev 서버,
  돼지꿈 hub 페이지 `h2 count: 2` — 고정 섹션 2개만, interpretation 파생 h2 없음).
- 신규 20개 Parent는 첫 섹션 "~은 보통 어떻게 해석할까?"(개요) + 실제 존재하는 Situation과
  자연스럽게 연결되는 섹션(예: "고양이의 색깔에 따라", "행동에 따라") 2~3개로 구성했다 —
  실제 존재하지 않는 상황을 위한 섹션은 만들지 않았다(지시문 §11).
- `app/dream/[keyword]/page.tsx`의 `generateMetadata()`도 함께 수정 — description이
  `## ` 마크업 기호를 그대로 노출하지 않도록 첫 순수 문단만 골라 slice하게 했다.

## 12. Situation 상세 구조

기존 Situation 상세 페이지 구조(제목/본문/핵심 해석/행운 숫자)는 그대로 유지했다. 신규
Situation도 동일한 필드(keyword/title/body/key_meaning/numbers/display_order)만 사용해
스키마 변경이 전혀 없다.

## 13. Duplicate Prevention (근접 중복 방지)

지시문 §13/§14 원칙에 따라, 검색 표현만 다른 근접 중복 Parent를 의도적으로 만들지 않았다 —
예: "물꿈"을 별도 Parent로 만들면 기존 "물에 빠지는 꿈"/"바다를 보는 꿈"과 겹쳐 제외했고,
"복권꿈"은 기존 "로또 당첨되는 꿈"과 검색 의도가 같아 별도 Parent 대신 그 Parent의
situation(`로또를-사는-꿈`)으로 흡수했다. Situation 단위 near-duplicate도 프로그래밍적으로
검증했다(§23).

## 14. Metadata

Parent(§11 참조)와 Situation 둘 다 기존 방식(고유 title/description, OG/Twitter) 그대로
유지 — 새 페이지도 동일 패턴을 따르므로 45개 Parent + 287개 Situation 전부 서로 다른 콘텐츠
기반 고유 metadata를 가진다(§23 SEO 샘플 감사에서 실측 확인).

## 15. Canonical

기존 `alternates: { canonical: path }` 로직을 그대로 재사용 — 새 Parent/Situation도 자동으로
self-canonical을 가진다. 새 코드 경로를 추가하지 않았다.

## 16. Breadcrumb

기존 4단계(홈→꿈해몽→Parent→Situation) BreadcrumbList JSON-LD를 그대로 재사용 — 신규
Parent/Situation도 자동으로 적용된다(§23 실측: 15개 신규 Situation URL 전부
`"@type":"BreadcrumbList"` 확인).

## 17. Internal Links (신규 구현)

지시문 §19/§20: Situation 상세 페이지 하단에 **"비슷한 꿈도 확인해보세요"** 섹션을 추가했다
(`app/dream/[keyword]/[situation]/page.tsx`). 복잡한 추천 엔진을 만들지 않고, 이미 있는
`getDreamSituations(dream.id)`(Parent hub 페이지가 쓰는 것과 동일한 함수, display_order
정렬)를 재사용해 같은 Parent의 다른 Situation 중 현재 항목을 제외한 최대 4개를 보여준다 —
지시문이 명시한 "same parent + display_order 등 단순 deterministic relation"을 그대로
구현했다. Parent 간 링크(§21)는 이번 Wave에서 추가하지 않았다 — 강제로 10개 링크를 넣지
않는다는 원칙과, 카테고리 nav가 이미 Parent 탐색을 제공한다는 점을 근거로 판단했다(다음
Wave 후보로 남김).

## 18. Dream Search UX (신규 구현)

지시문 §30/§31: `lib/api/dreamSearch.ts`(신규) — `dreams.keyword`/`dream_situations.title`·
`keyword`에 대한 Postgres `ilike` 쿼리 두 번만 사용한다(복잡한 semantic/AI 검색 없음). ilike
와일드카드 문자(`%`, `_`, `\`)는 이스케이프해 패턴 인젝션을 막는다. `GET /api/dream/search?q=`
(공개 API, 인증 불필요) + `components/dream/DreamSearchInput.tsx`(Client Component,
300ms debounce, 최대 8개 드롭다운 결과, 바깥 클릭 시 닫힘)로 `/dream` 페이지에 추가했다.

## 19. Sitemap

기존 `app/sitemap.ts`는 `dreams`/`dream_situations` 테이블을 직접 쿼리해 URL을 생성하므로
**코드 수정이 전혀 필요 없었다** — 마이그레이션만으로 자동 반영됐다. 실측(§23): 총 348개
`<url>` 중 `/dream/` 경로 340개 = Parent 45 + Situation 287 + Category 8(정확히 일치).
중복/404 URL 0건(코드 자체가 DB에서 직접 URL을 생성하므로 구조적으로 발생 불가).

## 20. Server Rendering

## 25. Admin Compatibility

새 column/table이 없고 기존 `lib/api/admin/dreams.ts`/`lib/api/admin/dreamSituations.ts`가
`dreamId`/`situationId` 기반으로 동작(하드코딩된 목록 없음)하므로, 신규 45개 Parent와 287개
Situation은 **구조적으로 기존 Admin CRUD에서 그대로 관리 가능하다**(지시문 §34/§35). 실제
관리자 세션으로 클릭 스루 검증은 이번 Task에서 수행하지 않았다(운영자 실제 로그인이 필요한
작업이라 범위 밖으로 판단) — 운영자가 `/admin/dreams`에서 신규 Parent들이 정상 노출/수정
가능한지 가벼운 스팟체크를 해보는 것을 권장한다.
