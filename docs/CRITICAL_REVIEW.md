# CRITICAL REVIEW — 15개 설계 문서 비판적 검토

> 검토자 관점: Product Reviewer / UX Reviewer / Software Architect Reviewer / SEO Reviewer / Growth Hacker / 투자 심사역
> 원칙: 설계자의 의도를 옹호하지 않고, 실패 가능성과 결함을 우선 탐색한다.

---

## 0. 총평 — 가장 치명적인 프레임 문제

**설계 전체가 "팀 개발"을 전제로 작성되어 있는데, 실제로는 1인 개발자 프로젝트다.**

이 사실 하나가 15개 문서 전체의 신뢰도를 흔든다. ROADMAP의 Phase 1(MVP, 8~10주)에는 AI 번호생성, 카카오로그인, 자동저장+당첨확인+알림, 카카오공유, 꿈해몽 200건+연계UX, 당첨사례, 가이드/FAQ, SEO 셋업, 관리자 패널이 모두 들어있다. 이걸 혼자 8~10주에 만든다는 것은 사실상 불가능하다. 투자 심사역 관점에서 이런 로드맵은 "우리는 일정을 검증하지 않았다"는 신호로 읽힌다.

**이 문제 하나를 고치지 않으면 나머지 개선안은 의미가 없다.** 아래 모든 항목보다 이것을 최우선으로 다뤄야 한다.

## 1. Product 관점

### 문제점
- **P-01 (Critical)**: MVP 범위 과다. 1인 개발자 기준 실현 불가능한 스코프.
- **P-02 (Critical)**: AI 운세를 "생년월일 기반 규칙 테이블(명리학 로직)"로 직접 구현하겠다는 계획은 난이도를 심각하게 과소평가했다. 정확한 만세력(연/월/일/시 간지 계산)과 오행 해석은 그 자체로 하나의 큰 프로젝트다. 이걸 1인 개발자가 "Phase 1 부속기능"처럼 다루는 건 위험하다.
- **P-03 (High)**: 배틀 `reward_description`이 텍스트 자유입력으로만 정의되어 있다. 현금·상품권성 보상으로 흘러갈 경우 경품고시·사행성 규제에 정면으로 걸린다 (§8 참조). 설계 단계에서 "비현금성 보상만 허용"이라는 제약이 문서에 없다.
- **P-04 (High)**: 친구 초대(레퍼럴) 기능이 FEATURE_SPEC 19개 기능 어디에도 없다. Growth 관점에서 이는 치명적 공백이다.
- **P-05 (Medium)**: 명예의 전당의 "실제 고액 당첨" 등재는 자진신고 기반인데 검증 수단이 전혀 없다. 허위 인증 시 신뢰도 붕괴 리스크.
- **P-06 (Medium)**: 실시간 번호 생성 로그는 재미는 있지만 실질 가치가 낮은 "허영 기능(vanity feature)"에 가깝다. Phase 2에 배틀·명예의전당과 나란히 배치된 것은 인프라 비용 대비 우선순위가 잘못됐다(§5, §9에서 재론).
- **P-07 (Low)**: 온보딩(첫 방문자 튜토리얼)이 어디에도 설계되어 있지 않다. 시니어 타겟을 표방하면서 첫 화면 설명 장치가 없는 건 모순이다.
- **P-08 (High)**: 19세 미만 이용 제한이 MASTER_PRD에 "선언"만 되어 있고, 실제 가입 시 검증 로직(체크박스든 뭐든)이 FEATURE_SPEC/ADMIN_REQUIREMENTS 어디에도 없다.

### 개선안
1. Phase 1 MVP를 "번호생성 → 카카오로그인 → 저장 → 당첨확인(수동 입력 기반)" 단일 루프로 축소하고, 꿈해몽/운세/배틀/커뮤니티는 Phase 1.5~2로 재배치.
2. AI 운세는 초기에 "간단한 규칙(띠+생월 기반 템플릿 조합)" 수준으로 낮추거나, LLM API 호출로 대체(직접 명리학 엔진 구현은 후순위). 정확도보다 "일관성 있고 재미있는 콘텐츠"가 목적임을 명시.
3. MASTER_PRD 비목표 조항에 "배틀/이벤트 보상은 현금·상품권을 지급하지 않으며 사이트 내 비현금성 보상(뱃지, 우선참여권, 소액 실물 굿즈)으로 한정한다"를 명문화.
4. 친구 초대 기능을 FEATURE_SPEC에 신규 기능(20번)으로 추가 (§4 Growth 참조).
5. 명예의 전당 "실제 당첨" 카테고리는 커뮤니티 인증(사진 업로드) + 관리자 수동 승인 절차를 명시하고, 미승인 상태는 노출하지 않음.
6. 가입 시 "만 19세 이상입니다" 체크박스 + 생년월일 기반 연령 검증 로직을 FEATURE_SPEC §7에 추가.

## 2. UX 관점

### 문제점
- **U-01 (Critical, 네이밍 충돌)**: 데스크톱 GNB의 "당첨사례"(타인의 당첨 스토리 열람)와 모바일 하단탭의 "당첨확인"(내 번호 당첨 여부 확인)이 이름이 거의 동일해서 사용자가 확실히 혼동한다. "3초 안에 원하는 기능을 찾는다"는 원칙에 정면으로 위배되는 설계 결함이다.
- **U-02 (High)**: 홈페이지 구조가 Hero→빠른실행카드→배틀배너→실시간로그→당첨하이라이트→명예의전당→콘텐츠추천→Footer까지 8개 섹션이다. "스크롤 최소화" 원칙을 스스로 어기고 있다.
- **U-03 (High)**: 배틀·명예의전당·커뮤니티가 모두 하단탭 "더보기" 안에 숨어있다. 사용자가 명시적으로 물어본 "배틀, 게시판을 3초 안에 찾을 수 있는가"에 대한 답은 "탭 2번 눌러야 한다"이며, 이는 설계자가 원했던 수준에 못 미친다.
- **U-04 (Medium)**: 비회원 세션 종료 시 노출되는 "회원가입 유도 모달(exit-intent)"은 모바일 환경에서 트리거가 불안정하고, 시니어 사용자에게는 "갑자기 튀어나오는 팝업"으로 인식되어 오히려 이탈을 유발할 수 있다.
- **U-05 (Medium)**: 가입 유도 타이밍이 문서마다 다르게 서술된다 — USER_FLOW는 "생성 직후 배너"(초반), USER_PSYCHOLOGY는 "2~5분 구간 배틀 진입 시"(중반)를 첫 로그인 요구 시점으로 각각 서술. 실제로는 몇 단계에서 몇 번 로그인을 요구하는지 하나로 정리되어 있지 않다.
- **U-06 (Low)**: 운세 입력 폼(생년월일/성별/태어난시간)이 단일 페이지인지 단계형 위저드인지 명시되지 않았다.
- **U-07 (Low)**: 공유 랜딩(`/share/[shareId]`)에서 친구의 운세를 구경한 뒤 "나도 보기" 버튼을 누르면 바로 생년월일 입력을 요구한다 — 콜드 트래픽에게는 마찰이 크다. 입력 없이 먼저 맛보기를 주는 장치가 없다.

### 개선안
1. "당첨확인"을 §10 신설 기능(행운 다이어리)으로 흡수·개명하여 명칭 충돌을 원천 제거 (아래 §10 참조). "당첨사례"는 그대로 유지.
2. 홈페이지 섹션을 로그인 여부에 따라 분기: 비회원은 Hero+빠른실행카드+배틀배너 3개 섹션만, 회원은 여기에 "내 다이어리 요약" 1개 섹션만 추가. 실시간 로그·콘텐츠 추천은 접이식(더보기 클릭 시 확장)으로 전환.
3. 배틀은 홈 화면 상단 배너로 이미 노출되므로 3초 요건 충족 가능. 다만 게시판(커뮤니티)은 하단탭에 없으므로, "더보기" 대신 홈 상단 빠른실행카드를 4→5개로 늘려 커뮤니티를 직접 노출하거나, 하단탭 구성을 "홈/번호생성/배틀/다이어리/더보기"로 재구성하고 운세·통계·커뮤니티를 더보기로 옮기는 재배치안을 검토.
4. exit-intent 모달을 제거하고, 페이지 하단에 항상 붙어있는 얇은 고정 배너("로그인하면 다음 주에도 이 번호를 기억해드려요")로 대체.
5. USER_FLOW와 USER_PSYCHOLOGY의 로그인 요구 시점을 하나의 표로 통일하여 두 문서에 동일하게 반영 (최초 소프트 유도: 생성 직후 배너(닫기 가능) / 하드 게이트: 배틀 참여·저장·다이어리 열람 시).
6. 공유 랜딩에서는 입력 없이도 "일반적인 오늘의 운세 미리보기"를 먼저 보여주고, 개인화된 결과는 입력 후 제공하는 2단계 구조로 변경.

## 3. SEO 관점

### 문제점
- **S-01 (High)**: **"로또 명당"(1등 배출 판매점) 키워드 클러스터가 완전히 누락**되어 있다. 한국에서 로또 관련 검색 중 최상위권 볼륨을 차지하는 키워드군인데 SEO_STRATEGY, FEATURE_SPEC, SITEMAP 어디에도 대응 페이지가 없다.
- **S-02 (High)**: "로또 당첨금 세금 계산기", "실수령액 계산기" 같은 계산기형 콘텐츠가 없다. 이런 툴 페이지는 백링크·체류시간·피처드 스니펫 확보에 매우 효과적인데 기회를 놓치고 있다.
- **S-03 (Medium)**: 백링크(Off-page SEO) 전략이 SEO_STRATEGY.md에 전혀 없다. 온페이지 최적화만으로는 경쟁 심한 Head 키워드에서 순위를 올리기 어렵다.
- **S-04 (Medium)**: 커뮤니티 UGC에 `DiscussionForumPosting` Schema를 적용하겠다고만 되어 있지, 실제로 이 게시글들이 검색엔진에서 얇은 콘텐츠(thin content)로 판정되지 않도록 하는 품질 기준이 없다.
- **S-05 (Low)**: AI 검색(Google AI Overview 등) 대응, 즉 구조화된 답변형 콘텐츠 최적화에 대한 언급이 없다. 2026년 기준 이미 무시할 수 없는 유입 채널이다.
- **S-06 (Medium)**: 지역 기반 SEO(로컬 SEO) 전략이 전무하다. §S-01과 직결된 문제.

### 개선안
1. 신규 콘텐츠 축: `/store` (판매점 찾기, 지도 기반), `/store/[storeId]` (개별 판매점 — 1등 배출 이력) 신설. 동행복권 공개 데이터(1등 배출점 명단)를 활용해 콘텐츠 자동 생성 가능 — SITEMAP, FEATURE_SPEC, DATABASE_SCHEMA(`stores` 테이블), CONTENT_STRATEGY에 반영.
2. `/tools/tax-calculator` (당첨금 세금 계산기) 신규 페이지 추가 — 개발 난이도 낮고 SEO 효과 큼. FEATURE_SPEC, SITEMAP에 반영.
3. SEO_STRATEGY에 "백링크 전략" 섹션 신설: 보도자료, 콘텐츠 제휴, 커뮤니티(디시/네이버카페 등) 자연 링크 유도 방안 명시.
4. 커뮤니티 게시글 최소 품질 기준(글자수, 이미지 포함 여부)을 만족하는 글만 `index` 처리하고 나머지는 `noindex` 처리하는 규칙을 SEO_STRATEGY에 추가.
5. FAQ/가이드 콘텐츠를 "짧고 명확한 Q&A 문단" 구조로 작성해 AI 검색 답변 채택 가능성을 높이는 작성 가이드를 CONTENT_STRATEGY에 추가.

## 4. Growth 관점

### 문제점
- **G-01 (High)**: 친구 초대(레퍼럴) 시스템 부재 (P-04와 동일 이슈, Growth 핵심 공백).
- **G-02 (Medium)**: 공유 콘텐츠가 정적 이미지 카드 1종뿐이라 바이럴 강도가 약하다. 비교·대결형 콘텐츠(한국에서 검증된 바이럴 포맷: MBTI 궁합, 사주 궁합류)가 없다.
- **G-03 (Medium)**: 출석/연속방문 스트릭 시스템이 없다. 습관 형성 앱(듀오링고류)의 핵심 리텐션 장치인데 설계에 빠져있다.
- **G-04 (Low)**: A/B 테스트나 그로스 실험 프로세스에 대한 언급이 어느 문서에도 없다.

### 개선안
1. `/invite` 레퍼럴 시스템 신설: 고유 초대 코드 발급, 친구 가입 시 양측에 비현금성 보상(예: "운세 상세보기 1회 무료" 또는 "배틀 우선참여권") 지급. FEATURE_SPEC 신규 기능, DATABASE_SCHEMA에 `referrals` 테이블 추가.
2. **"번호 궁합 테스트"** 신규 기능 제안: 내 번호와 친구 번호(또는 오늘의 운세)를 비교해 "궁합 점수"를 보여주는 가벼운 바이럴 콘텐츠. 한국 소셜미디어에서 검증된 포맷을 차용하되 사행성과 무관한 순수 재미 요소로 설계. Growth 임팩트가 클 것으로 예상되는 항목이라 우선 검토 권고.
3. 연속 방문 스트릭 배지 시스템(예: "3주 연속 방문 🔥") 도입 — 명예의 전당과 별도로 마이페이지/다이어리에 노출.
4. 초기에는 정식 A/B 테스트 도구 없이도 "가설-측정-변경" 로그를 남기는 간단한 실험 기록 관행을 IMPLEMENTATION_PLAN에 명시.

## 5. 데이터(Supabase) 관점

Supabase 사용을 전제로 재검토하면 DATABASE_SCHEMA.md는 **일반 RDBMS 설계에 머물러 있고 Supabase 고유 요소(Auth 통합, RLS, Storage)가 전혀 반영되지 않았다.** 이는 보안 설계의 실질적 공백이다.

### 문제점
- **D-01 (Critical)**: RLS(Row Level Security) 정책이 문서에 단 한 줄도 없다. Supabase는 기본적으로 RLS를 켜지 않으면 API를 통해 전체 테이블이 노출될 수 있는 구조라, 이 누락은 심각한 보안 리스크다.
- **D-02 (Critical)**: `users` 테이블이 Supabase의 `auth.users`와 어떻게 연결되는지 정의되어 있지 않다. 커스텀 `users` 테이블을 완전히 별도로 두면 Auth 기능(세션 관리, RLS의 `auth.uid()` 활용)을 제대로 못 쓴다. `profiles` 테이블이 `auth.users.id`를 FK로 참조하는 표준 패턴으로 재설계해야 한다.
- **D-03 (High)**: 카카오 로그인은 Supabase Auth의 기본 제공 OAuth 목록에 없다. 커스텀 OIDC 설정 또는 카카오 서버 인증 후 Supabase Admin API로 세션을 발급하는 방식이 필요한데, 이 기술적 난이도가 IMPLEMENTATION_PLAN에 전혀 언급되지 않았다. 사전 기술 검증(스파이크) 없이 "카카오 로그인 연동"을 1줄로 처리한 것은 리스크다.
- **D-04 (High)**: Storage 버킷 설계가 전혀 없다. 프로필 이미지, 커뮤니티 첨부, 공유 카드 이미지가 어디에 저장되고 어떤 접근 정책(public/private)을 가지는지 미정의.
- **D-05 (Medium)**: `dream_lookups` 테이블이 ERD 개요도에는 등장하지만 실제 테이블 정의 섹션에는 존재하지 않는다 — 문서 내부 불일치.
- **D-06 (Medium)**: `user_numbers.numbers`에 6개 숫자가 1~45 범위·중복없음을 보장하는 CHECK 제약이 명시되지 않았다.
- **D-07 (Medium)**: `community_posts`/`comments`의 `status='reported'` 자동전환만 있고, 신고자·신고사유를 기록하는 별도 `reports` 테이블이 없어 운영 감사가 불가능하다.
- **D-08 (Low)**: `admin_audit_logs.diff`(JSONB)에 생년월일 등 개인정보가 그대로 기록될 수 있는데 마스킹 규칙이 없다.
- **D-09 (High)**: 알림 테이블이 "1 notification = 1 channel" 구조라, 향후 이메일+웹푸시+알림톡을 동시에 보내려면 재설계가 필요하다 (§11에서 상술).

### 개선안
1. 모든 개인 데이터 테이블(`user_numbers`, `fortune_results`, `notifications`, `dream_journal_entries` 등)에 `auth.uid() = user_id` 기준 RLS 정책을 명시하는 별도 섹션을 DATABASE_SCHEMA에 신설.
2. `users` → `profiles`로 개명, PK를 `auth.users.id`(UUID) 참조로 재설계.
3. IMPLEMENTATION_PLAN에 "카카오 로그인 × Supabase Auth 통합 방식 사전 기술검증(PoC)"을 Phase 0 작업으로 명시.
4. Storage 버킷 설계 추가: `avatars`(공개), `community-uploads`(공개, 크기제한), `share-cards`(공개), 각 버킷 정책(RLS 유사한 Storage 정책) 명시.
5. `dream_lookups` 테이블을 실제로 정의하거나(사용자별 열람 이력 트래킹용) ERD에서 제거 — 둘 중 하나로 정합성 확보.
6. `user_numbers`에 `CHECK (array_length(numbers,1) = 6)` 등 제약 추가.
7. `reports` 테이블 신설(`id`, `target_type`, `target_id`, `reporter_id`, `reason`, `created_at`).
8. 감사로그 기록 시 개인정보 필드는 마스킹 처리 규칙 명시.
9. `notifications`를 `notifications`(내용) + `notification_deliveries`(채널별 발송 기록, 1:N) 구조로 분리.

## 6. 관리자 관점

### 문제점
- **A-01 (High)**: ADMIN_REQUIREMENTS가 `super`/`content_editor`/`community_manager` 3개 역할을 전제하는데, 1인 운영 현실과 맞지 않는 과설계다.
- **A-02 (High)**: 매주 당첨번호를 관리자가 수동 입력해야 하는데, 이는 공공데이터포털/동행복권 데이터를 통해 충분히 자동화 가능한 작업이다.
- **A-03 (Medium)**: 당첨 사례 콘텐츠 작성이 전량 수동이다. 반복 작업이라 자동화/반자동화 여지가 크다.
- **A-04 (Medium)**: 배틀을 매주 관리자가 새로 생성해야 한다 — 반복적인 정형 작업.
- **A-05 (Medium)**: 꿈해몽 대량 등록이 전량 수동 작성(초기 200건)으로 계획되어 있다. 1인 운영자에게는 상당한 부담.

### 개선안
1. 초기 관리자 역할을 `super` 단일 역할로 단순화. 역할 분리는 실제 팀원이 합류할 때 재도입.
2. 당첨번호 입력을 "공공데이터포털 로또 API 자동 수집 → 관리자 승인(더블체크 클릭 1번)" 방식으로 전환. 완전자동화가 아닌 승인 단계를 둬서 오류 리스크는 유지 관리.
3. 당첨 사례는 "AI 초안 생성(회차/등수/지역 데이터 기반 템플릿 문구 자동 생성) → 관리자가 검토 후 발행" 워크플로로 전환.
4. 배틀은 "직전 주 설정을 복제해 다음 회차로 자동 생성 → 관리자는 보상 문구만 수정 후 발행" 방식으로 전환.
5. 꿈해몽 콘텐츠도 "AI 초안 생성 → 관리자 검수·발행" 워크플로 도입 — 200건을 전량 수작업하는 대신 초안 생성 후 검수 시간만 투입.

## 7. 수익화 관점

### 현재 계획의 문제
현재 계획(광고, 쇼핑몰, 입점 수수료)은 모두 **Phase 3 이후에나 실현되는 장기 수익원**이다. 즉 최소 6개월 이상 매출이 0에 가깝다는 뜻이며, 이는 1인 개발자의 생존 가능성 문제로 직결된다. 투자 심사역 관점에서 "6개월간 무수익 구조"는 큰 리스크다.

### 개선안 — 추가 검토 가능한 현실적 수익 모델 (사행성 비조장 원칙 준수)
1. **연말/연초 결산 리포트 유료 판매** (스포티파이 랩드 스타일): §10 행운 다이어리 데이터를 활용해 "20XX년 나의 로또 한 해" PDF/카드 리포트를 유료(예: 1,900~3,900원)로 제공. 사행성과 무관하고, 다이어리 기능과 자연 연결되며, 공유까지 유도하는 1석3조 모델. **가장 먼저 검토할 것을 권고.**
2. **프리미엄 구독(Freemium)**: 월 정액으로 광고 제거 + AI 운세 상세버전 + 배틀 우선참여권 제공.
3. **제휴 마케팅**: 로또 판매점(§S-01 신규 콘텐츠와 연동), 사주/타로 서비스, 저축/적금 상품(당첨금 관리 콘텐츠와 자연 연결) 제휴 링크 수수료.
4. **브랜드 스폰서십**: 기업이 배틀 보상을 상품 협찬(현금 아님, §P-03과 일치) 형태로 제공하고 노출 대가를 지불하는 구조.
5. **비식별 트렌드 데이터 판매(B2B)**: 번호 생성 트렌드를 익명화·집계하여 언론/마케팅 리포트용으로 판매(개인정보 완전 비식별 처리 필요).

수익화 우선순위는 ROADMAP Phase 1에 "연말 결산 리포트"를, Phase 2에 프리미엄 구독을 배치하는 것을 권고한다.

## 9. 장기 확장성 관점

### 문제점
- **X-01 (Medium)**: 쇼핑몰 `products` 테이블에 향후 "입점 판매(마켓플레이스)"를 고려한 `seller_id` 개념이 없다. 지금 구조로는 입점 확장 시 스키마 전면 수정이 필요하다.
- **X-02 (Medium)**: 제휴 마케팅 추적을 위한 `affiliate_links`/`affiliate_clicks` 테이블이 없다.
- **X-03 (High)**: `user_numbers`가 저장·당첨확인 용도로만 설계되어 있어 §10 행운 다이어리가 요구하는 "구매여부/구매금액/생성 당시 추천 이유" 등을 담기엔 컬럼이 부족하다.
- **X-04 (Medium)**: 통계 캐시가 전체 통계용으로만 설계되어 있어 개인별 월간/연간 통계에는 대응하지 못한다.

### 개선안
1. `products`에 `seller_id BIGINT NULL`(자사 판매 시 NULL, 입점 시 판매자 참조)을 미리 추가해 향후 스키마 변경 최소화.
2. `affiliate_links`(id, partner_name, target_url, tracking_code), `affiliate_clicks`(id, link_id, clicked_at, referrer) 테이블을 Phase 3 확장 스키마에 사전 정의.
3. `user_numbers`에 컬럼 추가: `is_purchased`, `purchase_amount`, `recommendation_reason` (§10에서 상술).
4. `user_period_stats` 테이블 신설로 개인별 월간/연간 통계 지원 (§10에서 상술).

## 10. 신규 핵심 기능 — 행운 다이어리 (My Lucky Journal) 설계

### 10.1 목적
단순 저장소가 아니라 **"내 로또 인생의 기록"**을 통해 계정에 대한 소유감과 데이터 락인을 만들어 재방문을 구조적으로 강제하는 기능. §U-01에서 지적한 "당첨확인" 명칭 충돌 문제를 이 기능이 흡수함으로써 동시에 해결한다 — 하단탭 "당첨확인"을 "다이어리"로 개명하고, 당첨확인은 다이어리의 하위 구성요소로 통합한다.

| most_frequent_numbers | INT[] | |

> 개인별 데이터는 규모가 작으므로(사용자 1인당 레코드 수 제한적) "가장 많이 생성한 번호"류 통계는 캐시 없이 즉시 쿼리로 계산해도 무방하다. 사이트 전체 통계([[DATABASE_SCHEMA]] §3)만 배치 캐시가 필요하다 — 이 구분을 명확히 할 것.

### 10.4 UX 설계
- 마이페이지 최상단에 "나의 행운 다이어리" 카드를 가장 눈에 띄는 위치에 배치.
- 로그인 사용자의 홈 화면에는 "이번 달 요약" 위젯 노출: "이번달 12번 생성, 3번 구매, 최고기록 4개 일치" — 재방문 트리거로 기능.
- 연말/연초에 "20XX년 나의 로또 결산" 캠페인 콘텐츠를 자동 생성해 공유 유도 (§4 Growth, §7 수익화와 직결).
- **손익(지출 대비 당첨금) 표기는 신중하게 설계**: "재미로 보는 기록"으로 프레이밍하고, 과도한 지출 패턴 감지 시 "이번달 구매금액이 평소보다 많아요" 같은 책임감 있는 넛지를 포함할 것을 권고 — 이는 사행성 관련 법적/평판 리스크를 완화하는 효과도 있다 (§8 연동).

### 10.5 feasibility 주의사항 (반드시 인지할 것)
"구매여부/구매금액 자동 기록"은 동행복권이 개인별 구매내역을 공개 API로 제공하지 않으므로 **자동 검증이 불가능하며 자진 신고(수동 토글) 방식으로만 구현 가능하다.** 이를 "자동 추적"인 것처럼 사용자에게 오인시키는 문구는 사용하지 말 것. 향후 동행복권 계정 연동을 시도하는 것은 자격증명 보관 등 법적/보안 리스크가 매우 크므로 권장하지 않는다.

## 11. 알림 시스템 확장성 검토

### 11.1 구조적 문제
현재 `notifications.channel`이 단일 값(ENUM)으로 되어 있어 "하나의 알림을 여러 채널로 동시 발송"하는 시나리오(예: 당첨 시 인앱+이메일+웹푸시 동시 발송)를 감당하지 못한다. `notifications`(내용) / `notification_deliveries`(채널별 발송기록, 1:N) 구조로 분리해야 한다 (§D-09).

### 11.2 단계별 구현 가능 범위

**MVP (1인 개발, 사업자등록 전, 무료/저비용 가능)**
| 채널 | 구현 방법 | 비고 |
|---|---|---|
| 사이트 내 알림 | 자체 DB + 헤더 뱃지 | 완전 무료, 즉시 구현 가능 |
| 이메일 | Resend/Supabase 등 무료 티어 | 사업자등록 불필요, 발신 도메인 인증만 필요 |
| 웹 푸시 | Web Push API 또는 OneSignal 무료 티어 | 사업자등록 불필요. 단, iOS Safari는 PWA 설치 + iOS 16.4 이상 조건부 지원 — 전체 대응 아님을 인지할 것 |

**사업자등록 이후 (Phase 2+)**
| 채널 | 구현 방법 | 비고 |
|---|---|---|
| 카카오 알림톡 | 카카오 비즈니스 채널 개설 | 사업자등록번호 필수, 템플릿 사전 심사, 건당 발송비용 발생 |
| SMS/문자 | 문자중계사 계약 | 사업자 필수, 비용 발생, 광고성 메시지 규제 준수 |

이 구분을 IMPLEMENTATION_PLAN과 FEATURE_SPEC §10에 명시적으로 반영해, "지금 당장 무료로 할 수 있는 것"과 "사업자등록 후 할 것"을 혼동하지 않도록 해야 한다.
