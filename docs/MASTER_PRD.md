# MASTER PRD — Luck Platform

버전 2.0 · 개정일 2026-07-31 · 상태: Luck Platform 전환 반영

> v1.0(로또 플랫폼 단일 서비스)에서 v2.0(Luck Platform)으로 전면 개정. [[CRITICAL_REVIEW]]의 지적사항(1인 개발 현실 미반영, MVP 과다 등)을 반영한다.

## 0. 프로젝트 재정의 — Lotto Platform이 아니라 Luck Platform

이 프로젝트는 더 이상 "로또 번호 생성 사이트"가 아니다.

**로또는 이 플랫폼이 시장에 내놓는 첫 번째 서비스일 뿐이다.** 최종 목표는 행운과 관련된 모든 경험(운세, 꿈해몽, 통계, 기록, 커뮤니티, 상품)을 하나의 계정과 하나의 데이터 허브로 연결하는 **Luck Platform**을 만드는 것이다.

```
Luck Platform
├── Lotto          (로또 번호 생성/저장/당첨확인) — 1번째 출시 서비스
├── Lucky Journal  (행운 다이어리) — 플랫폼의 중심, 모든 기록이 모이는 곳
├── Dream          (꿈해몽)
├── Fortune        (AI 운세)
├── Statistics     (행운 통계)
├── Community      (행운 커뮤니티)
├── Winners        (당첨/행운 사례)
├── Shop           (행운 쇼핑몰)
├── Membership     (프리미엄 멤버십)
└── Partners       (제휴 입점/제휴 마케팅)
```

이 구조가 [[SITEMAP]]과 [[FEATURE_SPEC]]의 골격이 된다. 로또는 이 트리의 한 브랜치이며, 다른 브랜치(운세, 꿈, 통계 등)는 향후 로또 외 영역(예: 오늘의 운세만 보는 사용자, 타로/사주 관심층)으로도 독립적으로 확장 가능해야 한다.

### 핵심 재정의: 서비스의 중심은 번호 생성이 아니라 행운 다이어리다

과거 설계는 "번호 생성"을 입구이자 핵심 훅으로 봤다. 이는 틀리지 않았지만 불완전하다. 번호 생성은 **일회성 행동**이고, 행운 다이어리는 **누적되는 자산**이다. 사용자가 이 플랫폼에 재방문하는 이유는 "새 번호를 뽑기 위해서"가 아니라 "내 기록이 거기 쌓이고 있기 때문"이어야 한다.

```
번호생성 → 저장 → 당첨확인 → 꿈기록 → AI운세 → 통계 → 공유 → 쇼핑몰 → 멤버십
              └──────────────── 전부 [Lucky Journal]에 축적됨 ────────────────┘
```

상세 설계는 [[FEATURE_SPEC]] "행운 다이어리" 섹션 참조.

## 1. 프로젝트 배경 (Why Now) — 유지 및 확장

[[COMPETITOR_ANALYSIS]]에서 분석했듯 국내 로또 관련 사이트는 "도구형"과 "정보형"으로 양분되어 있고 습관화 장치가 없다. 여기에 더해, 국내 운세/사주 앱 시장 역시 로또·꿈해몽·번호와는 별개 시장으로 존재한다. **이 두 시장을 하나의 계정으로 묶는 플랫폼이 없다는 것이 Luck Platform의 기회다.**

## 2. 비전 선언문

> "번호를 뽑고, 꿈을 기록하고, 운세를 보고, 그 모든 걸 다이어리에 남기며 매주 돌아오는, 행운을 경험하는 하나의 공간."

## 3. 운영 원칙 — 1인 개발자 기준 (신규, 최상위 원칙)

**이 프로젝트는 스타트업 팀이 아니라 1인 개발자를 기준으로 설계된다.** 이는 부차적 제약이 아니라 모든 의사결정의 최우선 기준이다.

1. **운영 자동화 최우선**: 운영자가 매주 반복해야 하는 수동 작업은 설계 단계에서부터 자동화 경로를 함께 정의한다. 자동화 방법이 없는 기능은 채택하지 않는다.
2. **AI 위임 우선**: 콘텐츠 초안 작성, 반복적 데이터 입력, 신고 게시글 1차 필터링 등 AI가 대신할 수 있는 작업은 모두 AI에게 맡기고, 운영자는 승인/예외처리만 담당한다.
3. **관리 화면 최소화**: 관리자 페이지는 역할 분리, 세분화된 권한 체계 없이 단일 관리자 기준으로 단순화한다 ([[ADMIN_REQUIREMENTS]]).
4. **유지보수 비용 최소화**: 별도 서버 인프라(Redis, 전용 워커 서버 등)보다 관리형 서비스(Supabase 등)의 기본 기능을 최대한 활용한다 ([[IMPLEMENTATION_PLAN]]).
5. **확장성보다 현실성**: "나중에 팀이 커지면 필요할 구조"를 지금 만들지 않는다. 확장 여지는 스키마 설계 수준에서만 남겨두고(nullable 필드 등), 실제 복잡한 인프라는 필요해질 때 구축한다.

이 5원칙은 [[FEATURE_SPEC]], [[ADMIN_REQUIREMENTS]], [[IMPLEMENTATION_PLAN]], [[ROADMAP]] 전체에 관통 적용된다.

## 4. 프로젝트 목표 (Goals)

### 4.1 정성적 목표
- Luck Platform으로서 "행운과 관련된 모든 것을 기록하는 곳"이라는 포지션을 선점
- 1인 개발자가 지속가능하게 운영할 수 있는 구조로 출시 및 성장
- 40~70대도 불편 없이 사용하는 접근성 확보 (기존 원칙 유지)
- 행운 다이어리를 통한 실질적 습관화 달성 (번호생성 중심에서 기록 중심으로 리텐션 축 이동)

### 4.2 정량적 목표 (개정 — [[ROADMAP]] Phase 기준으로 재산정)
| 지표 | Phase 1 (MVP, ~1.5개월) | Phase 3 (다이어리 고도화 후, ~5개월) | Phase 7 (멤버십 출시 후, ~10개월) |
|---|---|---|---|
| MAU | 3천 | 3만 | 15만 |
| 회원가입 전환율 | 10% | 13% | 15% |
| 다이어리 주간 재방문율(회원 기준) | 20% | 35% | 45% |
| 평균 체류시간 | 1분 | 3분 | 5분 |
| 카카오 공유 건수/주 | 50 | 800 | 5,000 |

> v1.0 대비 목표 수치를 하향·현실화했다. 팀 기준의 낙관적 수치를 1인 개발/소규모 초기 트래픽 기준으로 재보정했다.

## 5. 핵심 가치 제안 (Value Proposition)

| 대상 | 제공 가치 |
|---|---|
| 일반 사용자 | "번호를 뽑고, 운세를 보고, 그 기록이 전부 내 다이어리에 남는다" |
| 40~70대 사용자 | "글씨 크고, 버튼 크고, 헷갈리지 않는 행운 기록 서비스" |
| 습관형 사용자 | "매주 다이어리를 열어보면 내 행운의 역사가 보인다" |
| 연말 회고형 사용자 | "1년치 행운 기록을 스포티파이 랩드처럼 결산 리포트로 받는다" |

## 6. 비목표 (Non-Goals) — 절대 하지 않을 것 (개정)

기존 원칙(도박/베팅 기능 금지, 당첨 보장 암시 금지, 미성년자 타겟팅 금지, 과도한 사행성 문구 금지)을 유지하며, 아래를 추가한다.

- **팀 전제 설계 금지**: 향후 팀이 생길 것을 가정하고 지금 복잡한 역할체계·마이크로서비스·중복 인프라를 만들지 않는다.
- **현금성 보상 금지**: 배틀·이벤트·레퍼럴 보상은 현금, 상품권 등 환금성 자산으로 지급하지 않는다. 사이트 내 비현금 혜택(뱃지, 우선참여권, 프리미엄 체험, 소액 실물 굿즈)으로 한정한다 (경품고시·사행성 규제 회피, [[CRITICAL_REVIEW]] §8).
- **미검증 나이 확인 방치 금지**: "19세 미만 이용 제한"을 선언만 하지 않고, 가입 절차에 실제 확인 단계를 포함한다 ([[FEATURE_SPEC]]).
- **구매내역 자동 추적 오인 유발 금지**: 행운 다이어리의 구매여부/금액은 사용자 자진 입력이며, 이를 "자동 추적"인 것처럼 표현하지 않는다 (동행복권 개인 구매내역 공개 API 부재).

## 7. 핵심 사용자 여정 (개정 — 다이어리 중심)

번호 생성 → 저장 → 당첨 자동 확인 → 꿈 기록 → AI 운세 → 통계 → 공유 → (장기) 쇼핑몰 → (장기) 멤버십

이 모든 단계의 데이터가 하나의 **행운 다이어리**로 수렴한다는 것이 v1.0과의 핵심 차이다. 상세 흐름은 [[USER_FLOW]] 참조.

## 9. 서비스 구조 및 기능 목록 (개정)

Luck Platform의 10개 브랜치별 대표 기능은 다음과 같다. 각 기능의 MVP 채택 여부는 [[ROADMAP]] §1 MoSCoW를 따른다.

| 브랜치 | 대표 기능 |
|---|---|
| Lotto | AI 번호 생성, 저장, 당첨 자동확인 |
| Lucky Journal | 히스토리, 캘린더, 월간/연간 리포트, 연말 Luck Report |
| Dream | 꿈 해몽, 꿈별 추천번호, 개인 꿈 기록 |
| Fortune | AI 운세 번호 (생년월일 기반) |
| Statistics | 로또 통계, 개인 통계 |
| Community | 게시판, 배틀, 명예의 전당, 친구 랭킹 |
| Winners | 실제 당첨 사례, 로또 명당(판매점) |
| Shop | 행운 상품(부적/굿즈/기념품) |
| Membership | 프리미엄 구독 |
| Partners | 입점 판매, 제휴 마케팅 |

상세 스펙은 [[FEATURE_SPEC]] 참조.

## 10. 성공 지표 정의 (North Star Metric) — 유지, 해석 보강

**North Star Metric = "주간 활성 회원 중 3개 이상 기능을 사용한 사용자 비율"**

v2.0에서는 이 3개 기능의 중심에 반드시 **행운 다이어리 열람**이 포함되어야 한다는 것을 명시한다. 다이어리를 거치지 않는 멀티기능 사용(예: 번호생성+통계만 반복)은 진짜 습관화로 보지 않는다.
